# WRITING STANDARD

**Document:** Repository Writing Standard

**Version:** 1.0.0

**Status:** Active

---

# Purpose

This document establishes the writing standards for every document contained within the Oryxus Brand Engine.

The objective is consistency.

Regardless of whether documentation is written by a human or AI, every document should feel as though it was authored by the same organization.

Writing style is part of the Oryxus methodology.

---

# Primary Objective

Every document should:

- Teach.
- Standardize.
- Scale knowledge.
- Support execution.
- Remain valuable for years.

Documentation should not exist merely to explain.

It should improve decision making.

---

# The Oryxus Writing Philosophy

Writing should prioritize:

```
Thinking

↓

Understanding

↓

Execution

↓

Consistency
```

Not

```
Words

↓

Length

↓

Decoration

↓

Complexity
```

---

# Writing Characteristics

Every document should be:

- Clear
- Structured
- Professional
- Practical
- Timeless
- Concise
- Complete
- Reusable

---

# Tone of Voice

Write like:

- A senior consultant.
- A systems architect.
- A product strategist.
- A technical author.

Do not write like:

- A marketer.
- A salesperson.
- A blogger.
- A social media creator.
- A chatbot.

---

# Writing Principles

## Principle 1

Explain **why** before explaining **how**.

Readers should understand the reasoning before learning the implementation.

---

## Principle 2

Teach concepts before procedures.

Understanding creates better execution.

---

## Principle 3

Use systems instead of opinions.

Recommendations should be supported by principles rather than personal preference.

---

## Principle 4

Optimize for long-term usefulness.

Avoid references that become obsolete quickly.

---

## Principle 5

Every paragraph should provide value.

Remove repetition.

Avoid filler.

---

# Document Structure

Every major document should follow this order where applicable.

```
Title

Purpose

Scope

Definitions

Core Principles

Methodology

Framework

Implementation

Examples

Checklist

Acceptance Criteria

References

Version History
```

The structure may be adapted when appropriate, but should remain recognizable across the repository.

---

# Heading Hierarchy

Use a logical heading structure.

```
H1

↓

H2

↓

H3

↓

H4
```

Avoid skipping heading levels.

Headings should describe content, not decorate it.

---

# Paragraph Guidelines

- Focus on one idea per paragraph.
- Keep paragraphs readable.
- Separate concepts clearly.
- Avoid unnecessary repetition.
- Prefer clarity over literary style.

---

# Lists

Use unordered lists when order is unimportant.

Use numbered lists for:

- Processes
- Sequences
- Procedures
- Checklists

Every list item should follow parallel structure.

---

# Tables

Prefer tables when comparing:

- Frameworks
- Features
- Methodologies
- Decisions
- Standards

Tables should improve readability rather than replace explanation.

---

# Diagrams

Use simple diagrams to explain relationships.

Example:

```
Research

↓

Strategy

↓

Experience

↓

Interface

↓

Development

↓

QA

↓

Delivery
```

Avoid decorative diagrams.

Every diagram should explain a concept.

---

# Terminology

Use one consistent term throughout the repository.

Avoid switching between similar words.

Example:

Correct

- Framework
- System
- Playbook

Incorrect

- Framework
- Method
- Model
- Guide

when referring to the same concept.

---

# Definitions

Every specialized term should be defined the first time it appears.

Definitions should be precise and reusable.

---

# Examples

Examples should:

- Demonstrate application.
- Reflect real-world situations.
- Reinforce methodology.

Avoid hypothetical examples unless necessary.

---

# Checklists

Where appropriate, conclude sections with checklists.

A checklist should enable a contributor to verify successful implementation.

---

# Acceptance Criteria

Every significant methodology should define measurable completion criteria.

Acceptance criteria answer:

> "How do we know this has been done correctly?"

---

# Markdown Standards

Use:

- Clear headings
- Code blocks for structures
- Tables for comparisons
- Horizontal rules between major sections

Avoid excessive formatting.

Formatting should improve navigation.

---

# Language Standards

Prefer:

- Active voice.
- Precise language.
- Specific terminology.

Avoid:

- Buzzwords.
- Marketing clichés.
- Unnecessary adjectives.
- Ambiguous statements.

---

# Cross-Referencing

Whenever a document depends on another document, reference it explicitly.

Example:

```
See:
00_ORYXUS_CONSTITUTION

Section:
Design Philosophy
```

The repository should function as an interconnected knowledge system.

---

# Revision Standards

When updating existing documentation:

- Preserve intent.
- Improve clarity.
- Remove duplication.
- Maintain terminology.
- Record methodology changes.

Avoid rewriting documents simply to change wording.

---

# Review Checklist

Before finalizing any document, verify:

- Purpose is clear.
- Scope is defined.
- Structure follows repository standards.
- Terminology is consistent.
- Content is actionable.
- Examples are relevant.
- Formatting is consistent.
- Acceptance criteria are present where applicable.

---

# Definition of Excellent Documentation

Excellent documentation should:

- Answer the reader's questions.
- Reduce future confusion.
- Eliminate repeated explanations.
- Improve execution quality.
- Remain valuable regardless of changing technologies.

---

# Final Principle

The quality of the Brand Engine is determined not by the number of pages it contains, but by the clarity, consistency, and usefulness of every page.

Every sentence should contribute to building a lasting knowledge system.

---

**End of Writing Standard**
