# DEFINITION OF DONE

**Document:** Repository Definition of Done

**Version:** 1.0.0

**Status:** Active

---

# Purpose

The Definition of Done (DoD) establishes the minimum completion requirements for every contribution made to the Oryxus Brand Engine.

A document is **not complete because it has been written.**

A document is complete only when it satisfies the quality, consistency, review, and governance standards defined by the repository.

The Definition of Done creates a single, measurable standard for completion across every repository asset.

---

# Why It Exists

As the repository grows into thousands of pages across multiple disciplines, contributors may have different interpretations of what "finished" means.

The Definition of Done eliminates this ambiguity by defining objective completion criteria.

Every completed document should reach the same level of quality regardless of:

- Author
- AI model
- Contributor
- Subject
- Document size

---

# Repository Principle

The repository values:

```
Complete Documentation

↓

Reviewed Documentation

↓

Versioned Documentation

↓

Trusted Documentation
```

Not

```
Written Documentation

↓

Uploaded Documentation

↓

Forgotten Documentation
```

Completion is measured by quality, not effort.

---

# Universal Completion Criteria

Every document must satisfy the following requirements before it is considered complete.

---

## 1. Purpose Defined

The document clearly explains:

- Why it exists.
- What problem it solves.
- Who should use it.

Purpose should be understandable within the first section.

---

## 2. Scope Defined

The document explicitly states:

- What is included.
- What is excluded.
- Dependencies.
- Related systems.

Scope prevents overlapping documentation.

---

## 3. Structure Complete

The document follows repository writing standards.

Where appropriate, it contains:

- Title
- Version
- Status
- Purpose
- Scope
- Principles
- Methodology
- Framework
- Implementation
- Examples
- Checklist
- Acceptance Criteria
- References

---

## 4. Methodology Complete

Methodology should:

- Explain reasoning.
- Describe execution.
- Support decision making.
- Be reusable.

Methodology should never rely on assumptions.

---

## 5. Repository Consistency

Verify:

- Terminology matches the Glossary.
- Writing follows the Writing Standard.
- Naming follows Naming Conventions.
- Versioning follows Versioning Standard.

Every document should integrate naturally into the repository.

---

## 6. No Duplication

Before approval verify:

- Similar documentation does not already exist.
- Existing documentation cannot be improved instead.
- New documentation adds unique value.

The Brand Engine should contain one authoritative source for each concept.

---

## 7. Examples Included

Where appropriate, provide:

- Practical examples
- Real-world scenarios
- Sample implementations
- Diagrams
- Tables

Examples should reinforce understanding.

---

## 8. Acceptance Criteria

If the document defines a process or methodology, measurable acceptance criteria should be included.

Acceptance criteria answer:

> "How do we verify successful implementation?"

---

## 9. Cross References

Related documentation should be referenced where appropriate.

Examples:

```
See:

00_ORYXUS_CONSTITUTION

↓

Design Philosophy

↓

Research System

↓

Quality Standard
```

The repository should function as an interconnected knowledge network.

---

## 10. Review Complete

Before approval, verify:

- Technical review completed.
- Structural review completed.
- Terminology review completed.
- Formatting review completed.
- Repository consistency confirmed.

No document should bypass review.

---

## 11. Version Assigned

Every completed document must contain:

```
Version

Status

Last Updated
```

Version information should match repository standards.

---

## 12. Changelog Updated

If methodology changed:

Update:

- CHANGELOG.md
- Repository Status
- Related references

Historical changes should remain traceable.

# Definition of Excellent

A document is excellent when it:

- Can be understood without additional explanation.
- Can be reused in future projects.
- Reduces future decision making.
- Improves repository consistency.
- Supports both human and AI contributors.
- Remains valuable over time.

Excellent documentation minimizes future uncertainty.

---

# Repository Integration

Once a document satisfies the Definition of Done, it should:

1. Receive a stable version.
2. Be linked from related documentation.
3. Be included in repository navigation.
4. Be tracked through version history.
5. Become the authoritative reference for its subject.

---

# Continuous Improvement

Completion does not prevent future improvement.

A completed document may evolve through:

- New insights
- Better methodology
- Improved examples
- Structural refinements

Every improvement should follow the Versioning Standard.

---

# Responsibilities

## Contributors

Responsible for:

- Following repository standards.
- Producing complete documentation.
- Performing self-review before submission.

---

## Reviewers

Responsible for:

- Verifying quality.
- Ensuring consistency.
- Protecting repository integrity.
- Approving stable releases.

---

## AI Contributors

Responsible for:

- Following AI Rules.
- Respecting repository hierarchy.
- Avoiding undocumented assumptions.
- Maintaining terminology consistency.

AI assists development but does not define repository standards.

---

# Completion Decision

A document should only be marked as **Done** when the answer is **Yes** to every question below.

- Does it solve its intended problem?
- Is the methodology complete?
- Is it reusable?
- Is it internally consistent?
- Does it align with repository philosophy?
- Has it been reviewed?
- Is it ready to become the repository's source of truth?

If any answer is **No**, the document is not complete.

---

# Final Principle

The Oryxus Brand Engine is designed to become the permanent operational knowledge base of Oryxus.

Every completed document should increase the value, reliability, and consistency of the repository.

The Definition of Done exists to ensure that "finished" always means **production-ready**, not merely **written**.
