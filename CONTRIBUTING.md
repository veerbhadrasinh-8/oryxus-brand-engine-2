# CONTRIBUTING.md

# Contributing to the Oryxus Brand Engine

**Version:** v1.0.0

---

# Purpose

This document defines the standards, workflow, review process, and quality expectations for every contribution made to the Oryxus Brand Engine.

The objective is not simply to create documentation.

The objective is to build a permanent knowledge system that remains valuable for years.

Every document added to this repository becomes part of the intellectual property of Oryxus and must meet the same quality standards regardless of whether it is written by a human or generated with AI assistance.

---

# Philosophy

Every contribution should improve one of the following:

- Clarity
- Consistency
- Reusability
- Scalability
- Quality
- Understanding

If a contribution does not improve at least one of these areas, it should not be merged.

---

# Source of Truth

The hierarchy of authority is:

1. Constitution
2. Core Systems
3. Frameworks
4. Templates
5. Playbooks
6. Skills
7. Prompts

If two documents conflict, the higher-level document always takes precedence.

---

# Document Lifecycle

Every document follows the same lifecycle.

## Stage 1 — Planning

Define:

- Purpose
- Scope
- Dependencies
- Deliverables

No writing begins until the scope is approved.

---

## Stage 2 — Research

Research should include:

- Industry standards
- Best practices
- Academic principles where relevant
- Real-world implementations
- Competitive methodologies

The repository should never rely solely on assumptions.

---

## Stage 3 — Drafting

The first draft should focus on completeness rather than perfection.

The objective is to capture the methodology.

---

## Stage 4 — Internal Review

Every document is reviewed for:

- Structure
- Accuracy
- Consistency
- Repetition
- Readability
- Practical usefulness

---

## Stage 5 — Revision

Feedback from the review stage is incorporated.

Only meaningful improvements should be made.

Avoid unnecessary rewrites.

---

## Stage 6 — Version Lock

Once approved:

- Assign Version 1.0
- Update CHANGELOG
- Reference from dependent documents

The document becomes the official standard.

# Document Structure

Every document should contain the following sections where applicable.

```
Title

Version

Purpose

Scope

Definitions

Core Principles

Methodology

Framework

Implementation

Examples

Checklist

Acceptance Criteria

References

Version History
```

This structure ensures consistency across the repository.

---

# Writing Standards

All documentation should be:

- Clear
- Professional
- Timeless
- Actionable
- Structured
- Concise without sacrificing depth

Avoid:

- Marketing language
- Buzzwords
- AI clichés
- Unverified claims
- Trend-based terminology

Write for long-term relevance.

---

# Markdown Standards

- Use descriptive headings.
- Use ordered hierarchy.
- Prefer tables for comparisons.
- Use fenced code blocks for workflows.
- Keep lists parallel.
- Maintain consistent spacing.
- Avoid excessive nesting.

# Versioning Policy

Development

```
v0.x.x
```

Stable

```
v1.x.x
```

Major methodology updates

```
v2.x.x
```

Minor edits should not change methodology.

Major revisions require documented reasoning.

---

# Commit Standards

Every commit should represent one logical change.

Good examples:

```
docs: add Constitution Part I

docs: complete Research System

framework: add Restaurant Framework

template: add PRD Template

skill: add UX Architect
```

Avoid vague commit messages such as:

```
Update

Changes

Fix

Work
```

---

# Quality Checklist

Before approving any contribution, verify:

- Purpose is clearly defined.
- Scope is documented.
- Structure follows repository standards.
- Terminology is consistent.
- Methodology is practical.
- Examples are relevant.
- Acceptance criteria are measurable.
- Version information is updated.

---

# Review Principles

During review, ask:

- Does this improve the repository?
- Is this reusable?
- Is it timeless?
- Is it internally consistent?
- Does it duplicate existing content?
- Can another contributor understand it?

If the answer is "No" to any question, revise before merging.

---

# AI Contribution Policy

AI is a collaborator, not the source of truth.

AI-generated content must:

- Follow repository methodology.
- Maintain consistency with existing documents.
- Be reviewed before acceptance.
- Never override established principles without explicit revision.

The repository owns the methodology.

AI assists with execution.

---

# Change Management

Changes should be:

- Intentional
- Documented
- Versioned
- Reviewed

Avoid unnecessary refactoring.

Stability is more valuable than constant change.

---

# Long-Term Maintenance

Every completed client project should be reviewed for lessons learned.

If a methodology improves, update the appropriate document.

Do not create duplicate approaches.

Improve the existing system instead.

---

# Acceptance Criteria

A contribution is considered complete when:

- It follows repository standards.
- It aligns with the Constitution.
- It passes internal review.
- It is versioned.
- It is recorded in the changelog.
- It can be referenced by future documents.

---

# Final Principle

Every contribution should make the Brand Engine easier to understand, easier to reuse, and more valuable than it was before.

The objective is not to write more documentation.

The objective is to build a lasting operating system for creating exceptional brands.
